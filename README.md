# 응달길 (EUNDALGIL) — 그늘만 밟고 가는 길

햇빛과 그늘을 계산해 걷기 좋은 길을 찾아주는 보행 지도 웹앱.
같은 시각·같은 목적지라도 **건물과 가로수 그림자**를 따라가는 경로를 최단 경로와 나란히 비교해 준다.

> 이름·색·아이콘·문구·알고리즘 구현은 모두 이 저장소에서 새로 만든 것이다.
> 지도 타일은 네이버 클라우드 플랫폼 Maps API를 정식으로 사용하고, 지형·건물·보행로 데이터는
> OpenStreetMap(ODbL)에서 받는다.

---

## 1. 실행

```bash
npm install
cp .env.local.example .env.local   # 키 입력
npm run dev
```

`http://localhost:3000` 접속.

### 네이버 지도 키 발급 (필수)

1. [네이버 클라우드 콘솔 → Application](https://console.ncloud.com/naver-service/application) 에서 Application 등록
2. 서비스에서 **Maps** 선택
3. **Web 서비스 URL** 에 `http://localhost:3000` 추가 (배포 시 실제 도메인도 추가)
4. 발급된 Client ID 를 `.env.local` 에 넣는다

```
NEXT_PUBLIC_NAVER_MAP_KEY_ID=발급받은_Client_ID
```

키가 없으면 지도 대신 발급 안내 화면이 뜬다. 나머지 UI는 그대로 동작한다.

### 장소 검색 (선택)

기본값은 OpenStreetMap **Nominatim** 이라 별도 키가 필요 없지만, 국내 상호 검색은 약하다.
네이버 검색 API 키를 넣으면 자동으로 그쪽을 쓴다.

```
NAVER_SEARCH_CLIENT_ID=...
NAVER_SEARCH_CLIENT_SECRET=...
```

## 2. 동작 원리

### 그림자 계산

1. `suncalc` 로 선택한 시각·좌표의 **태양 고도·방위각**을 구한다.
2. 그림자 길이 = `건물 높이 / tan(고도)`, 방향 = `태양 방위각 + 180°`.
3. 건물 바닥면을 그 방향으로 밀어낸 뒤, 원본과 이동본을 함께 감싸는 **볼록 껍질**을 그림자 폴리곤으로 쓴다.
   - ㄱ·ㄷ자 건물은 실제보다 조금 넓게 잡힌다. 수백 동을 매 프레임 다시 그리기 위해 정확한
     민코프스키 합 대신 택한 근사다. (`src/lib/shadow.ts`)
4. 가로수는 수관 원을 같은 방식으로 밀어내고, 차광 강도를 0.65로 둔다.
5. 폴리곤들을 60m 격자에 색인해 임의의 점의 차광도를 O(1)에 가깝게 조회한다.

건물 높이는 OSM `height` → `building:levels × 3.2m` → 용도별 기본값 순으로 추정한다.

### 경로 탐색

외부 길찾기 API는 **쓰지 않는다.** 그늘 비용을 간선마다 다르게 매겨야 하므로 보행 그래프를 직접 만든다.

1. OSM 보행 가능 도로를 받아 좌표 단위로 쪼갠 그래프를 만든다. (`src/lib/router.ts`)
2. 각 간선을 7m 간격으로 샘플링해 **그늘 비율 0~1** 을 채운다.
3. 간선 비용의 단위는 거리가 아니라 **체감 시간(초)** 이다.
   - 기본 소요 시간 = `길이 / (1.25m/s × 노면 배율)` — 계단 0.45배, 차도 갓길 0.95배, 공원길 1.05배
   - 횡단보도는 한 곳당 8초를 더한다
   - 여기에 `× (1 + 그늘선호도 × (1 − 그늘비율))` 로 햇빛 구간에 가산한다
   - "계단 회피"를 켜면 계단 시간에 2.5배를 더 곱한다 (실제 시간이 아니라 선호도)
   - 비용이 곧 시간이므로 **"최단" 경로는 화면에 뜨는 소요 시간 기준으로도 실제 최단**이 된다
4. A\*(직선거리 휴리스틱)로 **최단 경로**와 **그늘 경로**를 각각 구해 나란히 보여준다.
   두 경로가 사실상 같으면 하나만 남기고, 그 이유를 문구로 알린다.

실측(광화문 → 을지로입구, 직선거리 1.3km / 그늘 선호도 "그늘 우선"):

| 시각  | 태양 고도 | 최단 경로              | 그늘 경로                    |
| ----- | --------- | ---------------------- | ---------------------------- |
| 09:00 | 33°       | 1555m · 22분 · 그늘 49% | 1757m · 25분 · **그늘 64%**  |
| 12:00 | 58°       | 1555m · 22분 · 그늘 29% | 1646m · 23분 · **그늘 37%**  |
| 15:00 | 44°       | 1555m · 22분 · 그늘 52% | 우회해도 이득이 없어 미표시   |

그림자 계산 26ms, 그래프 구축 64ms, 경로 탐색 8ms (건물 4,425동 / 간선 6,993개 기준).

## 3. 구조

```
src/
  app/
    page.tsx              화면 조립 (browse / routeInput / routeResult)
    api/osm/route.ts      Overpass 프록시 + 10분 메모리 캐시
    api/search/route.ts   장소 검색 (네이버 지역검색 → Nominatim 폴백)
    api/diagnose/route.ts 지도 키 없이 엔진만 점검하는 개발용 엔드포인트
  components/
    MapView.tsx           네이버 지도 + 그림자 캔버스 오버레이 + 경로/마커
    TopBar / RouteHeader / RouteSheet / TimeBar / MapControls / BottomNav
    SearchOverlay.tsx     전체화면 검색
  lib/
    geo.ts       위경도·미터 변환, 볼록껍질, 리샘플링
    sun.ts       태양 위치
    shadow.ts    그림자 폴리곤 + 격자 색인
    router.ts    보행 그래프 + A*
    overpass.ts  Overpass 미러 지연 헤지 클라이언트
    useRouting.ts / store.ts / config.ts
```

### 개발용 점검

지도 키 없이도 계산 엔진이 도는지 확인할 수 있다.

```bash
curl "http://localhost:3000/api/diagnose?h=15"
```

### 주의: OneDrive 폴더

이 프로젝트는 지금 OneDrive 동기화 폴더 안에 있다. OneDrive 가 `.next` 를 실시간으로 동기화하면서
파일을 잠그면 개발 서버가 `EBUSY: resource busy or locked` 로 죽는다. 둘 중 하나를 하는 게 좋다.

- 프로젝트를 OneDrive 밖으로 옮긴다 (예: `C:\dev\eundalgil`) — 권장
- 또는 OneDrive 설정에서 `node_modules` 와 `.next` 를 동기화 제외로 지정한다

또한 `next dev` 가 떠 있는 상태에서 `next build` 를 돌리면 같은 `.next` 를 두 프로세스가 건드려
빌드가 깨진다. 하나씩 실행할 것.

## 4. 알아 둘 점

- **도보 5km 이내**만 안내한다. 그 이상은 받아야 할 OSM 데이터가 급격히 커진다.
- 공개 Overpass 미러는 망 환경에 따라 막히는 곳이 있다. `src/lib/overpass.ts` 는 1번 미러가
  7초 안에 답하지 않으면 2번을 겹쳐 부르는 식으로 넘어가고, 성공한 곳을 기억한다.
- 건물 높이·가로수는 OSM 등록 여부에 좌우된다. 서울 도심은 촘촘하지만 지방은 성길 수 있다.
  국내 정확도를 올리려면 국가공간정보포털의 건물통합정보(높이 포함)로 바꾸는 게 다음 단계다.
- 지형 경사는 아직 반영하지 않는다. OSM `incline` 태그만 읽어 두었고 비용에는 넣지 않았다.
