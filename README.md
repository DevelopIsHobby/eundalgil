# 응달길 (EUNDALGIL) — 그늘만 밟고 가는 길

햇빛과 그늘을 계산해 걷기 좋은 길을 찾아주는 보행·대중교통 지도 웹앱.
같은 시각·같은 목적지라도 **건물과 가로수 그림자**를 따라가는 경로를 최단 경로와 나란히 비교해 준다.
버스·지하철을 타는 구간에서는 **햇빛이 덜 드는 좌석 방향**까지 알려 준다.

> 이름·색·아이콘·문구·알고리즘 구현은 모두 이 저장소에서 새로 만든 것이다.
> 지도는 MapLibre GL JS 로 그리고, 타일·건물·보행로 데이터는 모두 무료로 열려 있는 것만 쓴다.
> **API 키가 하나도 없어도 그대로 실행된다.**

---

## 1. 실행

```bash
npm install
npm run dev
```

`http://localhost:3000` 접속. 키 설정은 필요 없다.

### 배경지도

| | 기본값 | 선택 |
| --- | --- | --- |
| 출처 | [OpenFreeMap](https://openfreemap.org/) `bright` | [브이월드](https://www.vworld.kr) `Base` |
| 키 | 필요 없음 | 무료 발급 필요 |
| 성격 | OSM 벡터 타일. 사용량 제한·요금 없음 | 국토교통부 래스터 타일. 국내 한글 표기·건물이 정확 |

기본값은 색이 제대로 들어간 `bright` 다. 처음엔 회색 일색인 `positron` 을 썼는데, 그늘은
잘 보여도 지도 자체가 안 읽혔다. 걷는 길을 고르는 앱이라 공원·건물·도로 등급이 색으로
구분돼야 한다. 그늘은 곱셈 합성으로 얹으므로 바탕이 화려해도 묻히지 않는다.

브이월드 키를 넣으면 지도 우측에 전환 버튼이 하나 더 생긴다.

> **브이월드 레이어 이름 주의**
> `Base` · `midnight` · `Hybrid` · `Satellite` · `white` 다섯 가지뿐이다. 다른 이름을 넣으면
> 타일 대신 `InvalidParameterValue` XML 이 와서 **지도가 조용히 빈 화면이 된다.**
> 줌은 6~18 까지고 (`Base` 만 19), `Satellite` 는 `.png` 가 아니라 `.jpeg` 다.
> 그늘만 보기엔 라벨이 거의 없는 `white` 가 더 깔끔하지만, 브이월드를 쓰는 이유가
> 국내 지명이므로 `Base` 를 기본으로 뒀다. (`src/lib/basemap.ts`)

```
NEXT_PUBLIC_VWORLD_KEY=발급받은_인증키
```

키는 [브이월드 오픈API](https://www.vworld.kr/dev/v4api.do) 에서 발급하고, 쓰려는 도메인
(개발 중이면 `localhost`)을 함께 등록해야 한다. 이 키 하나로 **배경지도와 장소 검색이 같이**
좋아진다. 검색은 서버에서 부르므로 노출을 피하고 싶으면 검색 전용 키를 따로 받아
`VWORLD_KEY` 에만 넣으면 된다.

키가 안 먹으면 서버 로그에 사유가 그대로 찍힌다. `INVALID_KEY` 는 오타,
`INCORRECT_KEY` 는 등록한 도메인과 다르다는 뜻이다. 후자는 `VWORLD_REFERER` 로 맞춰 준다.

```
[search] vworld: VWorld ADDRESS ERROR: INVALID_KEY — 등록되지 않은 인증키입니다.
```

### 장소 검색

"○○역" 을 치면 **지하철역을 먼저** 보여 준다. 역 이름은 버스정류장·출입구·도로 이름에도
그대로 들어가서, "봉천역" 을 쳤을 때 2호선 봉천역 대신 정류장이 먼저 잡히는 일이 있었다.
목적지를 정류장으로 잡으면 거기서 역까지 걷는 시간이 통째로 빠져 안내가 어긋난다.
같은 이름의 역이 여럿이므로 그중에서는 **지금 보고 있는 지도에서 가까운 것**을 먼저 둔다.

여기에 함정이 하나 더 있다. **OSM 은 국내 지하철역을 "역" 을 뗀 이름으로 적는다** —
상도역은 `상도`, 봉천역은 `봉천`, 숭실대입구역은 `숭실대입구` 다. 그래서 "상도역" 을
그대로 물으면 지하철역은 **한 건도** 안 나오고 같은 이름의 버스정류장만 잔뜩 나온다.
브이월드 키가 있으면 거기서 "지하철역" 이 나와 가려졌는데, 키 없이 띄운 배포판에서
그대로 드러났다. 그래서 "역" 으로 끝나는 질의는 **"역" 을 뗀 이름으로 한 번 더 묻고**
그중 지하철역만 골라 앞에 세운다. 화면에는 사람이 부르는 대로 "상도역" 으로 되돌려 적는다.
(그래야 같은 역이 `숭실대입구` · `숭실대입구역` 두 줄로 남지 않는다)

여러 곳을 동시에 물어 합친다. (`src/app/api/search/route.ts`) 앞에 놓인 것이 위에 뜨고,
**어느 하나가 죽어도 나머지 결과는 그대로 보여 준다.**

| 순서 | 출처 | 키 | 강점 |
| --- | --- | --- | --- |
| 1 | 브이월드 ADDRESS + PLACE | 필요 | 정부 도로명주소 DB. **건물명(`bldnm`)** 까지 찾는다 |
| 2 | Nominatim | 없음 | 주소를 정확히 적었을 때 잘 맞음. 상호 검색은 거의 안 됨 |
| 3 | Photon | 없음 | 부분 입력·상호에 강함. 엉뚱한 동네도 물어 와서 대한민국 bbox 로 자름 |

네이버 검색 키가 있으면 그쪽만 쓴다. 검색창은 지금 보고 있는 지도 중심을 같이 보내고,
2·3번은 그 좌표에 가까운 결과를 위로 올린다.

> **국내 건물명은 브이월드 키가 있어야 제대로 나온다**
> 2·3번은 같은 OSM 데이터를 본다. 한국 중소형 빌딩은 OSM 에 이름이 거의 등록돼 있지 않다.
> `삼성로86길 11` 의 거봉INC 는 OSM 어디에도 `name` 으로 없고 입주 점포의
> `addr:unit="거봉INC 지상2층"` 안에만 적혀 있다. 지오코더는 이 필드를 색인하지 않는다.
> (`영광빌딩`·`강남파이낸스센터`처럼 OSM 에 `name` 이 있는 건물은 키 없이도 잘 나온다.)

| 검색어 | 키 없음 | 브이월드 키 |
| --- | --- | --- |
| 거봉 inc | 0건 | **거봉INC빌딩** · 거봉INC입구 |
| 삼성로 86길 11 | 끌리메 삼성점(입주 점포) | **서울특별시 강남구 삼성로86길 11** · 지번 대치동 942-16 |
| 테헤란로 152 | 강남파이낸스센터 | 강남파이낸스센터 |

주소를 친 질의(도로명·행정구역·숫자만 남는 질의)는 **그 도로명이 들어 있지 않은 결과를 지운다.**
키가 없으면 Nominatim·Photon 이 엉뚱한 동네를 답인 척 내놓는데, 그러면 "주소가 없어졌다"고 느끼게 된다.
없으면 없다고 하고, 키가 없어서라면 그 이유를 검색창에 적어 준다.

도로명이 둘 섞인 질의("동작구 상도로 양녕로 22라길 56")는 주소 DB 도 헤맨다.
그럴 때는 가장 구체적인 도로명 + 건물번호("양녕로22라길 56")만 남겨 한 번 더 묻는다.
지선 표기("22라길")도 붙여 쓰도록 정규화한다 — 띄어 쓰면 한 건도 안 나온다.

브이월드는 `ADDRESS`(도로명주소)와 `PLACE`(상호·시설)를 따로 물어 번갈아 섞는다.
한쪽이 결과를 5건씩 쏟아 다른 쪽을 덮지 않게 하려는 것이다 — 예를 들어 "강남역" 은
`ADDRESS` 가 같은 이름의 오피스텔을 먼저 주고, 지하철역은 `PLACE` 쪽에 있다.

> **도로명 띄어쓰기 주의**
> 한국 도로명은 `삼성로86길` 처럼 길 번호를 붙여 쓴다. 사람은 `삼성로 86길` 로 띄어 쓰는 일이
> 많은데 그대로 보내면 Nominatim 이 한 건도 못 찾는다. `normalizeRoadName()` 이
> "…로/대로 + 숫자 + 길/번길" 일 때만 공백을 없앤다. (`테헤란로 152` 의 152는 건물번호라 그대로 둔다)

네이버 검색 API 키를 넣으면 국내 상호 검색이 가장 정확해진다. 있으면 그쪽만 쓴다.

```
NAVER_SEARCH_CLIENT_ID=...
NAVER_SEARCH_CLIENT_SECRET=...
```

## 2. 동작 원리

### 건물은 브이월드, 나머지는 OSM

그림자의 원천이 건물이라 이 데이터의 질이 곧 앱의 질이다. 건물만 **브이월드 건물통합정보**
(`LT_C_SPBD`)에서 받는다. (`src/lib/vworldBuildings.ts`)

| | 상도동 일대 1.2km × 1.0km |
| --- | --- |
| 공개 Overpass | 12~67초, 붐비는 밤에는 실패 |
| 브이월드 | 3,434동을 **1.4초** |

속도만이 아니라 **높이**가 다르다. OSM 국내 건물은 `height`·`building:levels` 가 대부분
비어 있어 기본값 12m 로 찍어야 했는데, 브이월드에는 지상 층수가 거의 다 들어 있다.
같은 범위에서 기본값에 기대는 건물이 **8%** 로 줄었다. 그림자 길이는 높이에 그대로
비례하므로 이 차이가 곧 그늘 정확도다. (상도동 → 중앙대 도보 경로의 그늘 6.4% → 24.8%)

브이월드가 안 되면 Overpass 로 건물까지 다시 받아 되돌아간다.

### 그림자 계산

1. `suncalc` 로 선택한 시각·좌표의 **태양 고도·방위각**을 구한다.
2. 그림자 길이 = `건물 높이 / tan(고도)`, 방향 = `태양 방위각 + 180°`.
3. 건물 바닥면을 그 방향으로 밀어낸 뒤, 원본과 이동본을 함께 감싸는 **볼록 껍질**을 그림자 폴리곤으로 쓴다.
   - ㄱ·ㄷ자 건물은 실제보다 조금 넓게 잡힌다. 수백 동을 매 프레임 다시 그리기 위해 정확한
     민코프스키 합 대신 택한 근사다. (`src/lib/shadow.ts`)
4. 가로수는 수관 원을 같은 방식으로 밀어내고, 차광 강도를 0.65로 둔다.
   한 그루씩 찍힌 `natural=tree` 만 읽으면 놓치는 게 많다 — 국내에서는 줄로 그어 둔
   `natural=tree_row` 가 더 흔하다. 그 선을 8m 간격으로 끊어 나무로 친다
   (상도동 일대: 0그루 → 69그루).
5. 폴리곤들을 60m 격자에 색인해 임의의 점의 차광도를 O(1)에 가깝게 조회한다.

건물 높이는 OSM `height` → `building:levels × 3.2m` → 용도별 기본값 순으로 추정한다.

그림자는 지도 위에 얹은 **2D 캔버스**에 그린다. 지도 레이어(GL fill)로 그리면 겹친 그림자가
겹친 횟수만큼 어두워져 얼룩덜룩해지는데, 캔버스는 폴리곤을 하나의 path 에 모아 nonzero 규칙으로
한 번만 채울 수 있기 때문이다. 지도와 어긋나지 않도록 MapLibre 의 `render` 프레임 안에서
동기적으로 그린다. (`src/components/MapView.tsx`)

캔버스에는 `mix-blend-mode: multiply` 를 건다. 반투명 회색을 덧칠하면 지도를 덮어 버려
그늘도 지도도 안 읽히는데, 곱셈은 밑에 있는 색을 **어둡게만** 만들어서 그늘 안의 길·글씨가
그대로 보인다. 그래서 캔버스에 칠하는 색은 "덧칠할 색" 이 아니라 "빛을 얼마나 깎을지" 에 가깝다.

### 경로 탐색

외부 길찾기 API는 **쓰지 않는다.** 그늘 비용을 간선마다 다르게 매겨야 하므로 보행 그래프를 직접 만든다.

1. OSM 보행 가능 도로를 받아 좌표 단위로 쪼갠 그래프를 만든다. (`src/lib/router.ts`)
   - **차도 터널은 뺀다.** 언덕을 뚫은 터널이 있으면 거리로만 보면 가장 곧은 길이라 경로가
     그리로 빨려 들어가는데, 실제로 그렇게 걷는 사람은 없다. (상도동 양녕로 터널에서 걸렸다)
     보행자용 지하도(`footway`·`steps`·`path` 에 붙은 `tunnel`)는 그대로 쓴다.
   - **램프(`*_link`)는 `ramp`, 포장 안 된 `path`·`track` 은 `trail` 로 따로 분류한다.**
     터널을 막으니 그 옆 `oneway` 연결로를 285m 걸었고, 연결로를 깎으니 이번엔 숲속
     산길(`natural=wood` 안의 태그 없는 `path`)로 갔다. 셋 다 "거리가 짧아서" 고른 길이다.
     아주 막으면 다른 길이 없을 때 경로가 끊기므로 배율로만 눌러 둔다.
2. **고도를 읽어 좌표마다 붙인다.** (`src/lib/elevation.ts`)
   - AWS Open Data 의 Terrain Tiles(terrarium)를 쓴다. 키도 요금도 없고, z14 한 장이
     약 1.9km 를 덮어서 경로 한 건에 한두 장이면 된다. 받은 타일은 메모리에 캐시한다.
   - `elevation(m) = R*256 + G + B/256 - 32768`
   - 한 픽셀이 7~8m 라 짧은 구간을 그대로 빼면 지형이 아니라 픽셀 잡음이 잡힌다.
     실제로 평지에서 오르막이 37m 로 부풀었다. 길마다 이동평균(5점)으로 다듬어 19m 가 됐다.
3. 각 간선을 7m 간격으로 샘플링해 **그늘 비율 0~1** 을 채운다.
4. 간선 비용의 단위는 거리가 아니라 **체감 시간(초)** 이다.
   - 기본 소요 시간 = `길이 / (걷는 속도 × 노면 배율)` — 계단 0.45배, 산길 0.5배, 램프 0.6배,
     차도 갓길 0.95배, 공원길 1.05배
   - **오르막 1m 당 6초를 더한다.** 등산에서 쓰는 네이스미스 규칙(600m 오르는 데 1시간)이다.
     내리막은 더하지 않는다 — 빨라지긴 해도 편한 건 아니라서 0으로 뒀다.
   - 횡단보도는 한 곳당 8초를 더한다
   - 여기에 `× (1 + 그늘선호도 × (1 − 그늘비율))` 로 햇빛 구간에 가산한다
   - "계단 회피"를 켜면 계단 시간에 2.5배를 더 곱한다 (실제 시간이 아니라 선호도)
   - 비용이 곧 시간이므로 **"최단" 경로는 화면에 뜨는 소요 시간 기준으로도 실제 최단**이 된다
5. **25m 보다 긴 간선은 잘라 중간에 노드를 심는다.** 출발지·도착지·정류장이 그래프에
   붙을 수 있는 자리는 **노드뿐**인데, 큰길과 자전거도로는 꺾이지 않는 한 점을 찍지 않아
   80~100m 동안 붙을 자리가 없는 구간이 흔하다. 봉천역 앞이 그랬다 — 정류장에서 6번 출구까지
   실제로는 39m 인데, 길 옆에 올라설 자리가 없어 80m 짜리 간선의 양 끝을 돌아 **173m·2.4분**
   짜리 답이 나왔다. 잘라 두니 **58m·0.8분**이 됐고, 같은 이유로 집 → 약수맨션도
   552m·7.8분에서 432m·6.2분으로 줄었다(그늘로 앱은 6분으로 본다).
   횡단보도만 자르지 않는다 — 대기 시간을 간선 하나당 한 번씩 세기 때문에, 자르면
   신호를 두세 번 기다리는 셈이 된다.
6. **출발·도착은 서로 이어진 덩어리에 붙인다.** 보행로 데이터는 통째로 이어져 있지 않다 —
   대학 캠퍼스 안길처럼 바깥과 끊긴 섬이 흔하다. 각자 가장 가까운 노드에 붙이면 서로 다른
   섬에 앉아 "경로 없음" 이 된다. (중앙대 서울캠퍼스에서 실제로 걸렸다) 그래서 그래프를 만들 때
   연결 덩어리 번호를 매겨 두고, 350m 안의 후보들 중 **같은 덩어리에 있는 조합**을 고른다.
7. A\*(직선거리 휴리스틱)로 **최단 경로**와 **취향 경로**를 각각 구해 나란히 보여준다.
   두 경로가 사실상 같으면 하나만 남기고, 그 이유를 문구로 알린다.

경로는 그림자와 달리 MapLibre 의 GeoJSON 소스 + line 레이어로 그린다. 선은 불투명해서 겹침
문제가 없고, 굵기·둥근 끝·파선을 지도가 직접 처리해 준다. 굵기는 줌에 따라 키운다 —
고정 폭이면 넓게 볼 때 실처럼 가늘어져 어느 길인지 알아보기 어렵다. 햇빛 구간도 그늘 구간과
같은 굵기의 실선으로 깔고 그 위에 흰 파선을 얹어, 경로가 끊겨 보이지 않게 했다.

실측(광화문 → 을지로입구, 직선거리 1.3km / 그늘 선호도 "그늘 우선"):

| 시각  | 태양 고도 | 최단 경로               | 그늘 경로                    |
| ----- | --------- | ----------------------- | ---------------------------- |
| 09:00 | 33°       | 1569m · 29분 · 오르막 16m · 그늘 30% | 1904m · 34분 · 오르막 8m · **그늘 64%** |
| 12:00 | 58°       | 1569m · 29분 · 오르막 16m · 그늘 6%  | 1711m · 31분 · 오르막 9m · **그늘 33%** |
| 15:00 | 44°       | 1569m · 29분 · 오르막 16m · 그늘 31% | 1672m · 32분 · 오르막 10m · **그늘 54%** |

**걷는 속도는 1.25m/s(4.5km/h)** 를 기본으로 쓰고, 취향에서 느긋하게(1.0)·빠르게(1.5)로 바꾼다.

한때 1.0m/s 로 두고 네이버 표기와 맞췄었다. 그때는 경사를 비용에 넣지 않아서 오르내림을
속도로 뭉뚱그려 흡수시킨 것이었는데, 지금은 오르막을 1m 당 6초로 따로 더하고 횡단보도
대기도 따로 세므로 기준 속도까지 느리게 두면 이중으로 깎였다. 실제로 상도동 531m 평지
구간을 9.3분으로 봤는데, 그 길을 걷는 사람도 그늘로도 6~7분으로 본다.

그림자 계산 26ms, 그래프 구축 64ms, 경로 탐색 8ms (건물 4,425동 / 간선 6,993개 기준).

### 취향

첫 실행 때 한 번 묻고(`src/components/Onboarding.tsx`), 나중에 오른쪽 위 아바타로 다시 연다.
고른 값은 `localStorage` 에만 저장되고, 서버로 보내지 않는다.

| 항목 | 고르는 값 | 경로 비용에 붙는 방식 |
| --- | --- | --- |
| 햇빛 취향 | 볕 쪽 / 균형 / 그늘 쪽 | 햇빛 구간(또는 그늘 구간) 시간에 배율 가산 |
| 언덕 | 피할래요 / 균형 / 괜찮아요 | 오르막 가산(1m 당 6초)에 최대 2.2배 |
| 계단 | 피할래요 / 균형 / 괜찮아요 (+ 완전 제외) | 계단 구간 시간에 최대 2.6배, 제외 시 간선 자체를 뺀다 |
| 길 분위기 | 조용하게 / 균형 / 활기차게 | 큰길(간선도로·6차선 이상) 또는 이면도로에 가산 |
| 걷는 속도 | 느긋하게 / 보통 / 빠르게 | 0.85 / 1.0 / 1.25 m/s. 소요 시간과 "최단" 판단이 함께 달라진다 |
| 우회 허용 | 최단 / 균형 / 여유 있게 | 위 가산들 전체에 0.5 / 1 / 1.7 배 |
| 야간 방범시설 | 사용 안 함 / 사용 | **해가 진 뒤에만**, 가로등·CCTV 가 먼 구간에 가산 |

가산은 전부 **1 이상의 배율**로만 붙인다. 비용이 실제 소요 시간보다 작아질 수 없어야
A\* 의 직선거리 휴리스틱이 그대로 유효하기 때문이다. "볕으로"를 골라도 그늘 구간에 가산을
붙이지, 햇빛 구간을 깎지 않는 이유가 이것이다.

### 대중교통

정류장 순서를 어디서 받든 **"정류장 목록 + 지나는 순서"** 한 모양으로 바꿔 쓴다.
출처는 셋이고, 버스는 앞에서부터 나오는 대로 쓴다. (`src/lib/transit.ts`, `src/app/api/transit/route.ts`)

| 출처 | 무엇 | 키 |
| --- | --- | --- |
| 서울 TOPIS (`seoulbus.ts`) | 서울 시내·마을버스 | 공공데이터포털 키 + **서울특별시 정류소/노선 정보 활용신청** (`ws.bus.go.kr`) |
| 국토교통부 TAGO (`tago.ts`) | 서울 밖 시내버스 | 공공데이터포털 키 (`TAGO_KEY`) |
| OpenStreetMap 노선 관계 | 지하철·경전철 | 없음 |

버스를 정부 API 로 받는 이유는 하나다 — **OSM 에 국내 시내버스가 거의 없다.**
TAGO 도 서울은 비어 있다시피 해서(강남·사당 근처 몇 개뿐) 서울은 TOPIS 를 쓴다.
키가 없거나 활용신청 전이면 그 사실을 화면에 적고 지하철만 안내한다.
서울 열린데이터광장(data.seoul.go.kr) 키로는 **정류소 좌표와 노선 목록까지만** 나오고
노선별 정류장 순서가 없어 길찾기에 못 쓴다. 그래서 서울도 공공데이터포털 키를 쓴다.

타고 내리는 정류장이 같은 조합은 하나로 합치고, 나머지 노선 번호는 "이것도 탈 수 있다" 로
붙인다. 상도4동약수맨션 → 중대후문입구 를 동작08·동작10·동작21 이 함께 다니는 식이다.

지하철 노선은 OpenStreetMap 의 **노선 관계(route relation)** 에서 읽는다.

1. 출발지·목적지 반경 800m 의 정류장 노드를 찾고, **그 정류장을 지나는 노선 관계만** 받는다.
   노선에 속한 나머지 정류장 좌표는 `node(r)` 재귀로 따라온다 — 노선의 주행 way 는 받지 않는다.
   (도시 하나의 버스 노선을 통째로 받으면 수십 MB 다)
2. 정류장 순서는 **PTv2 방식(`stop`·`platform` 역할)만 믿는다.** 역할이 비어 있거나
   `forward`/`backward` 로 두 방향을 한 관계에 몰아넣은 옛 데이터는 "몇 번째 정류장"이
   성립하지 않아 통째로 버린다. 버린 뒤에도 연속한 정류장이 3km 넘게 튀는 노선이 12% 를
   넘으면 순서가 뒤섞인 것으로 보고 역시 버린다. 잘못된 순서를 쓰면 **타서 반대편으로 가는**
   안내가 나온다.
3. **정류장은 거리가 아니라 노선으로 고른다.** 봉천역 앞처럼 같은 이름 정류장이
   촘촘한 곳에서는 가장 가까운 여섯 곳이 전부 "봉천역" 으로 채워지고, 정작 타야 할
   노선이 서는 "봉천역.관악초등학교"(162m)가 밀려난다. 실제로 500번 직행이 후보에서
   빠져 환승 경로가 추천되던 버그가 여기서 났다. 그래서 가까운 순으로 보되
   **이미 잡은 정류장에 없는 노선을 더해 주는 곳만** 남긴다.
4. 직행과 1회 환승을 찾는다. 환승 지점은 지도상 거리가 아니라 **여기까지 걸린 시간** 순으로
   40곳만 남긴다. 거리로 자르면 한 번 지나쳤다가 다른 노선으로 되돌아오는 흔한 환승을 놓친다.
5. 소요 시간은 정류장 사이 직선거리와 수단별 표정속도(버스 16km/h, 지하철 32km/h)로 추정하고,
   배차 평균의 절반(버스 4분, 지하철 3분)을 대기 시간으로 더한다. **추정값이다.**
6. **타서 가까워지지 않는 조합은 버린다.** 승·하차 정류장의 목적지까지 거리 차이가
   주행 거리의 35% (또는 250m) 는 돼야 한다. 이게 없으면 목적지 반대쪽으로 한 정거장 갔다가
   되돌아 걷는 경로가 만들어진다. 접근·하차 도보 합이 직선거리의 1.15배를 넘어도 버린다.
7. **정류장까지 걸어갈 길이 없으면 그 여정을 통째로 버린다.** 예전에는 직선으로 이어 버려서,
   상도터널처럼 사람이 걸어서 지날 수 없는 곳을 "16분 걷기" 라고 우기는 안내가 나왔다.
   (정류장 코앞 120m 이하의 틈만 직선으로 메운다)
8. 실제 도보 구간까지 계산한 뒤, **걷는 것보다 느린 대중교통은 뺀다.**
9. 정류장까지 걷는 구간·환승 도보·내려서 걷는 구간은 위의 그늘 경로 탐색을 그대로 돌린다.
   그래서 시트의 "그늘 / 최단" 토글은 **같은 노선을 타되 도보 구간만 바꿔** 보여 준다.
10. **목적지가 "○○역" 이면 역 한복판이 아니라 출입구로 안내한다.** (`stationArrival()`)
    OSM 의 `railway=subway_entrance` 중 목적지 250m 안에 있는 것들을 모아, 가까운 다섯 곳을
    **실제 경로로 재 보고 가장 빨리 닿는 곳**을 고른다. 직선거리로 고르면 길 건너 출구를
    집어 신호 두 번을 건너는 답이 나온다. 이름이 있으면 "봉천역 6번 출구" 로 적는다.

### 자리 추천

버스·지하철에서 햇빛이 덜 드는 쪽을 고른다. (`src/lib/seat.ts`)

1. 정류장을 이은 주행 경로를 구간마다 쪼개고, 각 구간의 **진행 방위각**을 구한다.
2. 그 시각·그 지점의 태양 방위각과의 차이 `θ` 로 좌우를 가른다 — `sin θ > 0` 이면 오른쪽 창이다.
3. 노출량 = `Σ 구간길이 × |sin θ| × cos(태양 고도)`.
   고도를 곱하는 건 해가 높으면 지붕이 가려 옆 창으로 덜 들어오기 때문이다.
4. 노출이 적은 쪽을 추천하고, `1 − 노출/전체길이` 를 "그늘 %" 로 적는다.
   좌우 차이가 5%p 미만이면 "앞뒤에서 들어와 차이가 거의 없다"고 알린다.
5. 주행 시간에 맞춰 해도 같이 움직인다 — 긴 노선은 타는 동안 태양 위치가 달라진다.

지하 구간은 알 수 없다. 지하철에는 "지상 구간 기준"이라고 적어 둔다.

### 무더위쉼터

그늘이 끊기는 구간에서 **잠깐 들어가 쉴 곳**까지 알려 준다. 서울 열린데이터광장의
무더위쉼터(`TbGtnHwcwP`, 4,084곳)에 좌표와 **운영요일·운영시간**이 들어 있어서,
화면에 띄운 시각 기준으로 문을 연 곳만 고를 수 있다. (`/api/shelters`)

- 목록을 범위로 잘라 주지 않아, 하루 한 번 통째로 받아 두고 범위만 잘라 응답한다
- 걷는 구간에서 120m 안에 있는 곳만 "지나는 길에 있다" 로 본다
- 그늘이 70%를 넘는 구간에는 띄우지 않는다 — 필요할 때만 보여야 눈에 들어온다

### 출발 시각 추천

경로가 정해진 뒤, **같은 길 위에서 해만 옮겨** 30분 간격으로 세 시간을 다시 잰다.
길을 다시 찾지는 않는다 — 길이 바뀌면 "같은 길이 시원해진다" 는 말이 아니게 된다.
지금보다 그늘이 10%p 넘게 늘어나는 시각이 있을 때만 한 줄 띄운다.

> 오후 6:00에 나서면 같은 길이 그늘 75% (지금 39%)

### 길 안내

`안내 시작` 을 누르면 위치를 따라가며 다음에 할 일을 알려 준다. (`src/lib/guide.ts`)

- 안내 문구는 **경로 모양에서만** 뽑는다. 좌표마다 어느 길인지를 우리가 들고 있지 않아서,
  길 이름을 붙이면 엉뚱한 골목 이름을 말하게 된다. "120m 앞 왼쪽으로" 는 이름 없이도 따라간다
- 32°보다 크게 꺾일 때만 안내하고, 18m 안에서 잇달아 꺾이면 한 번만 말한다 (골목 지그재그)
- 45m 넘게 벗어난 위치가 **세 번 연달아** 들어오면 이탈로 본다. 한 번 튄 좌표로 놀라게 하지 않는다
- 회전이 60m 안으로 들어오면 한 번 **소리로** 읽어 준다 (같은 안내를 두 번 말하지 않는다)
- 걷는 동안 화면이 꺼지지 않게 Wake Lock 을 잡는다. 화면을 다시 켜면 잠금이 풀리므로
  `visibilitychange` 에서 다시 잡는다. 지원하지 않는 브라우저에서는 그냥 없이 간다
- 다시 찾기는 **출발지를 지금 자리로 바꾸는 것**으로 끝낸다 — 재계산 경로를 따로 두지 않는다

### 저장

출발·도착만 저장한다(`localStorage`). 경로 자체를 얼려 두면 시각·취향·실시간이 바뀐 뒤에
틀린 안내가 되므로, 다시 열 때 그 시점 기준으로 새로 찾는다.

### 날씨

지도 중심의 기온·**체감온도**·습도·자외선을 [Open-Meteo](https://open-meteo.com/) 에서 받는다.
키가 필요 없고 상업적 이용도 허용한다. 실패하면 카드를 그냥 안 그린다. (`/api/weather`)

"그늘 52%" 는 비율이라 와닿지 않는다. 시트에는 **"햇빛 아래 613m · 체감 18°"** 로 적는다 —
몇 미터를 몇 도에서 걷는지가 실제로 궁금한 것이다.

### 지도 데이터는 타일로 미리 받아 둔다 (서울 한정)

공개 Overpass 는 붐빌 때 한 요청에 수십 초가 걸리고, 넷 다 죽는 밤도 있다. 무엇보다
**공개 미러는 앱 트래픽을 태우라고 열어 둔 곳이 아니다.** 그래서 운영 중에는 아예 부르지
않는다 — 서울 전체를 미리 받아 저장소에 함께 둔다.

- **고정 격자 0.04°** (약 3.5km × 4.4km), 서울이 **96타일** (`src/lib/tiles.ts`)
- 요청한 범위를 덮는 타일을 합쳐서 응답한다. 예전에는 요청 범위 모양 그대로 캐시해서,
  출발지를 한 블록만 옮겨도 캐시가 통째로 빗나갔다
- 타일은 `data/osm-tiles/<스키마>/x_y.json.gz` 에 gzip 으로 둔다 (`src/lib/tileStore.ts`).
  **프로젝트 안**이라 배포에 함께 실려 간다 — 임시 폴더에 두던 예전 캐시는 배포마다 사라졌다
- 좌표는 6자리(11cm)로 줄여 담는다. 길에 올라서는 판정이 25m, 정류장 맞추기가 150m 라
  그 이상은 필요 없다. 60MB → 48MB 가 된다
- `TILE_SCHEMA` 는 **Overpass 질의나 걸러내는 규칙을 바꿀 때 반드시 올린다.**
  안 올리면 옛 규칙으로 걸러진 타일이 그대로 쓰인다
- 노선이 지나는 정류장 순서는 여전히 디스크 캐시에 남긴다 (`src/lib/diskCache.ts`).
  서울 버스 한 노선이 0.3~1초씩 걸리고 한 번에 수십 개를 부르기 때문이다

타일이 없는 자리는 그때 받아서 저장한다. 그래서 개발 중에는 평소처럼 쓰면 되고,
미리받기는 "서울의 모든 타일을 한 번씩 요청하는 것" 일 뿐이다.

```
npm run warm          # 개발 서버(3000)를 통해 서울 96타일을 받는다
npm run warm -- 3100  # 다른 포트로
```

이미 받아 둔 타일은 건너뛰므로 **도중에 끊기면 다시 실행하면 이어서 받는다.**
공개 미러에 예의를 지키려고 한 장씩 순서대로 받고 1.5초씩 쉰다.

서울 밖 범위는 422 로 거절한다. 전국을 담으려면 타일을 그만큼 더 받아야 한다.

`/api/diagnose` 응답의 `tiles` 에 지금 몇 장이 얼마나 쌓였는지 나온다.

### 철도 노선도 미리 받아 둔다

버스는 TOPIS 가 실시간으로 주지만, 지하철·광역전철 노선은 OSM 에서 온다.
노선과 선로는 몇 달에 한 번 바뀔까 말까 한 자료라 길찾기마다 물어볼 이유가 없다.

- 서울 범위의 철도 노선을 **한 번에 통째로** 받아 `data/rail/seoul-<스키마>.json.gz` 에 둔다
- 타일과 달리 격자로 자르지 않는다. 노선은 서울을 가로질러 뻗어 있어 자르면 역 순서가 끊긴다
- 선로 좌표만 서울 범위로 자른다. 1호선처럼 천안까지 가는 노선을 통째로 받을 수는 없다
- 길찾기 때는 **출발지나 목적지 걸어갈 거리 안에 역이 있는 노선만** 골라 보낸다.
  서울 전체를 그대로 보내면 응답만 커진다
- `npm run warm` 이 타일을 다 받은 뒤 이것도 한 번 받는다


### 줌 단위 주의

MapLibre 의 줌은 512px 타일 기준이라 네이버·구글의 256px 기준보다 **한 단계 낮다.**
(MapLibre z15 ≒ 네이버 z16) `src/lib/config.ts` 의 값들은 모두 MapLibre 기준이다.

### 개발용 점검

지도 없이도 계산 엔진이 도는지 확인할 수 있다. 화면의 설정을 그대로 재현할 수 있게
`from`·`to`(`경도,위도`), `h`(기준 시각), 그리고 취향(`sun`·`hill`·`steps`·`vibe`·`detour`,
`excludeSteps=1`)을 받는다. `transit=1` 을 붙이면 대중교통 조합까지 함께 본다.

```bash
curl "http://localhost:3000/api/diagnose?h=15&from=126.94649,37.49779&to=126.94778,37.50289&sun=shade"
curl "http://localhost:3000/api/diagnose?h=15&from=127.0276,37.4979&to=127.1002,37.5133&transit=1"
```

`transit` 응답에는 받은 정류장·노선 수와 후보 조합이 그대로 들어 있다.

```
stops 1321 patterns 56
18.1분 환승0 접근1m 하차도보137m
    2: 강남 → 잠실 (6개 정류장)
```

응답 첫머리의 **`elevationOk`** 를 먼저 본다. `false` 면 DEM 을 못 받아 **오르막이 비용에 안 들어간
상태**이고, 그러면 언덕을 넘는 경로가 나올 수 있다. 서버 로그에도 `[elevation]` 경고가 찍힌다.

응답의 `streets` 에 **경로가 지나는 길이 순서대로** 나온다. "왜 이런 길로 가지?" 싶을 때
여기부터 보면 된다 — 차도 터널·램프를 타고 있는지가 바로 드러난다.

```
[fast] 1013m 18.6분
   양녕로22라길 (road) 32m
   (이름 없음) (footway) 147m
   상도로38길 (steps) 21m
   ...
```

앱과 같은 범위(`max(400m, 직선거리×0.45)`)로 데이터를 받으므로 화면 결과와 일치한다.
다만 `/api/osm` 이 10분간 캐시하므로, 필터를 고친 직후에는 좌표를 조금 흔들어 캐시를 비켜 가야 한다.

### 주의: MapLibre 는 5.x 로 고정한다

**6.x 로 올리지 말 것.** 6.8.0 에서는 아이콘(심볼)을 쓰는 스타일이 통째로 렌더되지 않는다.
`bright`·`liberty` 를 띄우면 배경색만 칠해진 빈 화면이 되고 콘솔에
`InvalidStateError: The source image could not be decoded.` 가 타일 수만큼 찍힌다.

우리 코드 문제가 아니라는 건 확인했다.

- 같은 브라우저에서 CDN 으로 받은 6.8.0 도 똑같이 실패한다
- 같은 브라우저·같은 스타일을 5.9.0 으로 띄우면 정상이다
- 스프라이트 PNG 디코딩은 메인 스레드·워커 양쪽 모두 정상이다 (직접 `createImageBitmap` 확인)

심볼 레이어를 전부 지우면 6.x 에서도 그려지므로, 아이콘 아틀라스를 만드는 쪽 문제로 보인다.
회색 일색인 `positron` 은 아이콘을 안 써서 6.x 에서도 멀쩡했기 때문에 한동안 드러나지 않았다.

덤으로 5.x 는 워커가 번들 안에 들어 있어서, 6.x 에서 필요했던 워커 파일 복사
(`setWorkerUrl` + `public/maplibre/`) 가 아예 필요 없다.

### 주의: OneDrive 폴더 (dev 는 predev 가 지켜 준다)

OneDrive 동기화 폴더 안에 두면 OneDrive 가 `.next` 를 실시간으로 동기화하면서 파일을 잠가
개발 서버가 `EBUSY: resource busy or locked` 로 죽는다. 둘 중 하나를 하는 게 좋다.

- 프로젝트를 OneDrive 밖으로 옮긴다 (예: `C:\dev\eundalgil`) — 권장
- 또는 OneDrive 설정에서 `node_modules` 와 `.next` 를 동기화 제외로 지정한다

### 주의: dev 와 build 는 `.next` 를 같이 쓴다

`next dev` 와 `next build` 는 같은 `.next` 폴더에 서로 다른 형식으로 쓴다. 한쪽 산출물 위에
다른 쪽을 올리면 이런 오류가 난다.

```
Error: Cannot find module './787.js'
Require stack:
- .next\server\webpack-runtime.js
- .next\server\pages\_document.js
```

`.next` 에 `BUILD_ID` · `404.html` · `*.nft.json` 이 보이면 production 빌드 산출물이 남아 있다는
뜻이다. **서버를 먼저 내리고**(안 그러면 Windows 에서 파일이 잠겨 삭제가 실패한다) 지운 뒤 다시 띄운다.

```bash
rm -rf .next && npm run dev
```

## 4. 알아 둘 점

- **도보 5km 이내**만 안내한다. 그 이상은 받아야 할 OSM 데이터가 급격히 커진다.
- 공개 Overpass 미러는 망 환경에 따라 막히는 곳이 있다. `src/lib/overpass.ts` 는 1번 미러가
  7초 안에 답하지 않으면 2번을 겹쳐 부르는 식으로 넘어가고, 성공한 곳을 기억한다.
- 건물 높이·가로수는 OSM 등록 여부에 좌우된다. 서울 도심은 촘촘하지만 지방은 성길 수 있다.
  국내 정확도를 올리려면 국가공간정보포털의 건물통합정보(높이 포함)로 바꾸는 게 다음 단계다.
- **대중교통은 OSM 에 등록된 노선만 안내한다.** 수도권 지하철은 촘촘하지만 시내버스는
  지역 편차가 크다. 노선이 있어도 정류장 순서가 옛 방식이면 위의 규칙에 걸려 버려진다.
  실제로 관악·상도 구간에서 500번 버스 관계가 하나 잡혔지만, 두 방향 정류장이 섞여 있어
  제외됐다. 국내 정확도를 올리려면 국토교통부 TAGO 나 ODsay 같은 노선 API 를 붙이는 게 다음 단계다.
- 대중교통 소요 시간·요금은 **추정값**이다. 배차·혼잡·환승 할인을 반영하지 않는다.
- 방범시설(가로등·CCTV)도 OSM 등록분만 본다. 서울 도심도 한 구간에 열 개 남짓이라
  야간 경로가 최단과 같아지는 일이 흔하다. 그럴 때는 시트에 이유를 적어 준다.
- OpenFreeMap 은 기부로 굴러가는 무료 서비스다. 트래픽이 커지면
  [자체 호스팅](https://openfreemap.org/quick_start/)이나 브이월드로 옮기는 걸 고려할 것.
